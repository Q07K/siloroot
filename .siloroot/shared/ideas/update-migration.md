# 업데이트 스킬과 마이그레이션 정책

프로젝트 폴더 구조 2판을 확정하고 이 작업 공간을 새 구조로 옮기는 이야기를 하다가 나왔다(`shared/ideas/project-folder-layout.md`).

## 왜 (사용자)

- 플러그인이 버전업하면서 이런저런 것이 많이 바뀐다.
- 그런데 과거 버전 작업 공간을 새 버전에 맞추는 마이그레이션 정책이 하나도 없다.
- 그래서 `update` 스킬을 두는 것이 어떤지 고민해 달라.

## 지금은 어떻게 하고 있나 (AI가 코드를 보고 확인)

| 장치 | 하는 일 | 한계 |
| --- | --- | --- |
| init 다시 실행 | 관리 블록(`siloroot:start`~`end`)을 새 템플릿으로 바꾼다 | 블록 밖 문서와 폴더는 건드리지 않는다 |
| `STALE_CHECK` | `metadata-guide.md`, home:feedback/README.md에 새 type이나 폴더 규칙이 빠졌으면 경고만 한다 | 고치는 것은 사용자 몫 |
| 옛 배치 그대로 읽기 | `layout`이 없는 설정은 예전 배치(flat)로 읽어 계속 돌게 한다(0.2.0) | 옛 배치를 새 배치로 옮기는 길은 없다. 옛 방식을 영원히 함께 지고 간다 |
| `config.json`의 `version: 1` | 설정 모양의 번호 | 쓰는 곳이 없다. 작업 공간이 어느 플러그인 버전으로 만들어졌는지도 남지 않는다 |
| 훅 | 뷰어를 켜고 할 일을 알린다 | 작업 공간이 플러그인보다 뒤처졌는지는 보지 않는다 |

## AI 제안 (아직 정하지 않음)

### 1. 작업 공간이 자기 버전을 안다

`config.json`에 작업 공간 모양 번호(`schema`)와 마지막으로 맞춘 플러그인 버전을 적는다. 플러그인은 자기가 기대하는 `schema`를 안다.

### 2. 마이그레이션을 플러그인에 담는다

```
migrations/
  001-wrap-siloroot-folder.mjs     flat → wrapped (0.2.0)
  002-project-areas.mjs            01-log… → shared/, private/, 홈 (다음 구조)
```

- 하나에 번호 하나, 순서대로만 돈다. 각각 "무엇을 바꾸나"를 미리 보여 주는 계획(dry-run)과 실제 적용을 둘 다 가진다.
- 기계적인 일(폴더 옮기기, 문서 안 경로 바꾸기, 관리 블록 바꾸기)은 스크립트가 한다. 토큰이 들지 않는다.
- 판단이 필요한 일(이 아이디어가 공유인가 개인인가, 이 노트의 개념과 사건을 어떻게 나누나)은 AI가 제안하고 사용자가 승인한다. 지금의 "후보 → 승인" 흐름과 같다.

### 3. 알리고, 사용자가 돌린다

- 세션이 시작될 때 훅이 작업 공간 `schema`와 플러그인을 견준다. 뒤처졌으면 "[SiloRoot] 업데이트할 것이 있습니다"로 알리기만 한다. 저절로 바꾸지 않는다.
- `/siloroot:update`가 하는 일:
  1. 바뀌는 것 미리 보기: 옮겨질 파일, 바뀔 경로, 새 규칙
  2. 승인받기 (판단이 필요한 항목은 하나씩)
  3. 되돌릴 수 있게 남기기: `.siloroot/`는 바깥 git에서 빠져 있어 git으로 되돌릴 수 없다. 바꾸기 전 상태를 통째로 백업한다
  4. 순서대로 적용
  5. 점검: 뷰어 다시 만들기, 속성 경고, 끊어진 연결
  6. 작업 기록에 한 줄
- 사용자가 고친 문서는 덮어쓰지 않는다. 관리 블록 밖, 사용자가 손댄 안내 문서는 차이를 보여 주고 고르게 한다.

### 4. 개발 규칙에 넣을 것

- 템플릿, 폴더, 속성 값, 설정 모양이 바뀌는 버전은 마이그레이션을 함께 낸다. 이 저장소 `CLAUDE.md`의 "올리기 전 확인"에 한 줄 더한다.
- 테스트: 옛 버전 모양의 작업 공간(예시 데이터)을 마이그레이션해서 새 버전과 같아지는지 본다.
- 옛 배치를 계속 읽는 호환 코드는 마이그레이션이 생기면 몇 버전 뒤에 걷어 낸다.

## 지금 하려던 일과의 관계

이 작업 공간을 새 구조(`shared/ideas/project-folder-layout.md`)로 옮기는 일이 곧 첫 큰 마이그레이션이다. 업데이트 장치를 먼저 만들고 이 작업 공간을 첫 시험 대상으로 쓰면, 손으로 옮기는 일을 한 번만 하지 않고 다른 사용자에게도 같은 길을 줄 수 있다.

**정함 (2026-11-24, 사용자):** 업데이트 장치를 먼저 만든다. 그래야 구조 분리가 업데이트로 저절로 된다.

AI가 덧붙인 것: 저절로 되는 범위와 아닌 범위가 있다.

| 순서 | 할 일 | 저절로 되나 |
| --- | --- | --- |
| 1 | 업데이트 장치: 작업 공간 버전, 마이그레이션 틀, 알림 훅, `/siloroot:update`, 백업 | (만드는 일) |
| 2 | 새 구조를 플러그인에 정의: project와 personal 모드 init, 규칙 블록, 새 type, 홈 위치 설정 | (만드는 일) |
| 3 | 옛 구조 → 새 구조 마이그레이션(`002`) | 폴더 옮기기, 경로 바꾸기, 규칙 블록 바꾸기는 저절로 된다. 문서마다 공유인가 개인인가, 공부 노트의 개념과 사건 나누기는 AI가 제안하고 사용자가 승인한다 |
| 4 | 이 작업 공간에 `/siloroot:update`를 돌려 첫 시험 | |

**구현 (2026-11-24):** 1단계를 계획(`shared/plans/update-migration-decision-plan.md`)대로 만들어 PR #22(0.4.0)로 올렸다. 다음은 머지 뒤 이 작업 공간에서 `/siloroot:update`를 돌려 보기, 그다음 구조 분리 마이그레이션(`002`) 설계다. `002` 전에 "뒤 마이그레이션을 앞 것이 끝난 상태 기준으로 계획하기"를 고쳐야 한다(PR #22의 미룬 것).

**머지 (2026-11-24):** PR #22를 머지했다. `main`은 0.4.0이다.

**나누기 (2026-11-25, 사용자):** 업데이트 스킬을 가벼운 update와 무거운 migrate로 나눈다(`shared/decisions/update-split-by-weight.md`). 설계는 `shared/design/update-split-design.md`.
