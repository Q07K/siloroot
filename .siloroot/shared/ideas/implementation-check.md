# 구현 점검: 구현이 컨벤션과 설계를 따랐나

`shared/ideas/workspace-modes.md`의 "두 모드의 목적"에서 나왔다. 프로젝트 모드에서 검증하는 고리로, 공부 모드의 채점(`/siloroot:verify`)과 짝이 된다. 논의 과정은 private/discussions/2026-11-24-implementation-check.md에 있다.

## 지금 (사용자)

- AI에게 리뷰를 시키지만 제대로 확인하지는 못한다.
- 가끔 생각나면 코드를 직접 한 번씩 본다.
- 프론트엔드는 공통 컴포넌트로 만들라고 했는데, 쓰다 보면 디자인이 다르게 보이는 것으로 어긋남이 확 드러난다.

## AI가 본 원인

| 원인 | 모습 |
| --- | --- |
| 규칙이 대화에만 있다 | "공통 컴포넌트로 만들어라"를 대화에서 말했을 뿐, 다음 작업의 AI가 읽는 문서에 없으면 휘발된다(원하는 것 1, 2번과 같은 뿌리) |
| 점검 시점이 우연이다 | 생각날 때, 혹은 화면이 어긋나 보일 때에야 드러난다 |
| 찾은 어긋남이 남지 않는다 | 고치고 끝나서, 같은 어긋남이 다시 생긴다 |

## AI 제안 (아직 정하지 않음)

- 컨벤션을 공유 영역의 문서로 둔다. 점검은 그 문서에 비춰 한다.
- 점검 결과는 규칙마다 지켰다·어겼다·판단 못 함으로 남긴다.
- 어긋남을 찾으면 컨벤션을 더 분명히 할 후보를 만들고, 사용자가 승인하면 컨벤션에 넣는다. 지금의 "글쓰기 규칙 후보 → 승인" 흐름과 같다.
- 규칙을 둘로 나눌 수 있다. 스크립트로 기계적으로 볼 수 있는 규칙(예: 공통 버튼 대신 `<button>`을 직접 쓴 곳 찾기)과 AI가 판단해야 하는 규칙. 앞쪽은 토큰이 들지 않는다.

## 강제할까, 사용자에게 맡길까

사용자 고민: 점검은 PR 전이나 요청할 때 하는 게 맞다고 본다. 그런데 SiloRoot가 강제해야 할 부분인가, 사용자가 알아서 구성하게 해야 하나. PR 전이라면 PR을 쓸 수 있는 환경이어야 하고, GitHub가 아닌 다른 것으로 코드를 관리하는 사람은 어떻게 하나.

AI 제안: "무엇을 점검하나"와 "언제 돌리나"를 떼어 낸다.

| 나눔 | 누가 맡나 | 모습 |
| --- | --- | --- |
| 점검 자체 | SiloRoot | 스킬 하나(예: `/siloroot:check`). 컨벤션과 설계 문서를 읽고, 바뀐 코드를 보고, 규칙마다 결과를 남기고, 어긋남을 후보로 올린다. 코드 관리 도구와 상관없이 돈다 |
| 알림 | SiloRoot (기본으로 켜짐) | 막지 않고 알리기만 한다. 코드가 바뀌었는데 점검하지 않았으면 대화가 끝날 때 "[SiloRoot] 처리할 일"에 띄우고, 뷰어에 "마지막 점검 뒤 바뀐 파일 N개"를 보인다. Claude Code 훅으로 돌아서 GitHub도 git도 필요 없다 |
| 관문 | 사용자 (원하면) | PR, 커밋 훅, CI에 걸어 막는 것은 사용자가 고른다. SiloRoot는 거는 법(GitHub Actions, GitLab CI, git 훅 예시)만 문서로 준다 |

- SiloRoot는 지식 도구이지 CI가 아니다. 막는 일은 팀의 개발 환경이 정할 일이다.
- "바뀐 코드"를 찾는 법은 git이 있으면 기준 브랜치와의 차이, 없으면 마지막 점검 때 남긴 파일 지문과의 차이로 한다. 뷰어가 문서에 쓰는 "지난번과 비교" 방식과 같다.

**확정 (2026-11-24, 사용자):** 위 세 갈래로 한다. 점검 자체는 SiloRoot의 스킬, 알림은 기본으로 켜고 막지 않는다, PR·커밋·CI에 거는 관문은 사용자가 고르고 SiloRoot는 거는 법만 문서로 준다.

## 열린 질문

- 점검 결과를 어디에 어떤 모양으로 남길지.
- 스크립트로 볼 규칙과 AI가 판단할 규칙을 컨벤션 문서에서 어떻게 구분해 적을지.
