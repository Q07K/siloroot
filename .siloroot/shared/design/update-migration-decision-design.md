# 업데이트 장치 설계 (1단계)

`shared/ideas/update-migration.md`에서 "업데이트 장치를 구조 분리보다 먼저 만든다"로 정한 뒤 쓴 설계다. 이 문서만 읽고 계획을 세울 수 있게 쓴다. "AI가 정함"이라고 적은 것은 사용자가 따로 정하지 않아 AI가 고른 것이다.

## 1. 왜

- 플러그인은 버전마다 템플릿, 폴더, 속성 값, 규칙이 바뀐다. 그런데 예전 버전으로 만든 작업 공간을 새 버전에 맞추는 길이 없다.
- 지금은 "옛 모양도 계속 읽어 주기"로 버틴다. `layout`이 없는 설정은 예전 배치(flat)로 읽고, init을 다시 돌리면 관리 블록만 바뀌고, 안내 문서에 새 항목이 빠졌으면 경고만 한다(`scripts/init.mjs`의 `STALE_CHECK`). 옮기는 길은 없다.
- 다음 단계에서 작업 공간 구조가 크게 바뀐다(`01-log`, `02-study`… → `shared/`, private/, 홈. `shared/ideas/project-folder-layout.md`). 이것을 손으로 옮기면 이 작업 공간 하나만 옮겨지고, 다른 사용자는 같은 길을 못 간다.
- 그래서 업데이트 장치를 먼저 만들고, 구조 분리는 그 위에 올라가는 마이그레이션 하나로 만든다.

## 2. 목표, 하지 않을 것, 실패로 볼 것

**목표**
- 작업 공간이 자기가 어떤 모양(버전)인지 안다.
- 플러그인이 옛 모양에서 새 모양으로 가는 마이그레이션을 담고, 순서대로 돌린다.
- 뒤처진 작업 공간을 세션 시작 때 알린다.
- `/siloroot:update` 하나로 미리 보기 → 승인 → 백업 → 적용 → 점검 → 기록까지 간다.
- 되돌릴 수 있다.
- 첫 실제 마이그레이션으로 예전 배치(flat) → 감싼 배치(wrapped)를 담는다(`001`).

**하지 않을 것 (이번 단계)**
- 새 구조(`shared/`, private/, 홈, project와 personal 모드) 정의와 그 마이그레이션(`002`). 다음 단계다.
- 저절로 적용하기. 알리기만 한다.
- 플러그인 자체 설치나 버전 올리기. 그것은 Claude Code 플러그인 관리(`/plugin`)가 한다. 이 장치는 "설치된 플러그인 버전에 작업 공간을 맞추는" 일만 한다.

**실패로 볼 것 (돌아가도 실패)**
- 사용자 문서 내용이 사라지거나 덮어써진다.
- 팀이 같이 쓰는 파일(`.gitignore`, 프로젝트 맨 위 `CLAUDE.md`의 블록 밖)을 사용자 승인 없이 바꾼다.
- 되돌리기가 안 된다.
- 업데이트 중간에 실패했는데 작업 공간이 반쯤 바뀐 채로 어떤 상태인지 알 수 없다.
- 알림이 매 메시지마다 붙어 토큰을 계속 쓴다.

## 3. 지금 코드에서 닿는 곳

| 파일 | 지금 | 바뀌는 것 |
| --- | --- | --- |
| `lib/config.mjs` | `version: 1`, `port`, `layout`, `dirs`를 읽고 쓴다. `layout`이 없으면 flat | `schema`, `plugin`을 읽고 쓴다. 없을 때 추정하는 규칙 |
| `scripts/init.mjs` | 없는 파일만 만들고 관리 블록을 맞춘다. 옛 배치는 그대로 따른다 | 새 작업 공간에 `schema`, `plugin`을 적는다. 뒤처진 작업 공간이면 `warnings`로 업데이트를 안내한다(옮기지는 않는다). 관리 블록 맞추기를 업데이트가 다시 쓸 수 있게 함수로 내보낸다 |

| `.claude-plugin/plugin.json`, `package.json` | 0.3.x | 0.4.0 |
| `README.md`, `README.ko.md` | | `/siloroot:update` 설명 |
| 저장소 `CLAUDE.md` | 올리기 전 확인 | 마이그레이션 정책 한 줄 |

## 4. 설계

### 4.1 작업 공간 버전

`config.json`에 두 칸을 더한다.

```json
{ "version": 1, "port": 4180, "layout": "wrapped", "schema": 2, "plugin": "0.4.0" }
```

| 칸 | 뜻 |
| --- | --- |
| `version` | 설정 파일 모양 번호. 지금처럼 1로 둔다 |
| `schema` | 작업 공간 모양 번호. 폴더 배치, 문서 위치, 속성 규칙처럼 마이그레이션이 필요한 변화가 있을 때만 오른다 |
| `plugin` | 이 작업 공간을 마지막으로 맞춘 플러그인 버전. 관리 블록이나 안내 문서처럼 옮기지 않고 새로 맞추면 되는 변화를 알아채는 데 쓴다 |

- 플러그인은 코드에 `SCHEMA`(지금 2)를 가진다.
- `schema`가 없으면 추정한다: `layout`이 `wrapped`면 2, 아니면(flat) 1. AI가 정함.
- `plugin`이 없으면 "알 수 없음"으로 보고 관리 블록 맞추기를 권한다.

### 4.2 마이그레이션

`lib/migrations/` 아래 파일 하나에 마이그레이션 하나. 번호 순서대로만 돈다.

```js
export default {
  id: '001-wrap-siloroot-folder',
  from: 1, to: 2,
  title: '문서를 .siloroot/ 안으로 감싼다',
  plan(ctx) { return { moves, edits, decisions, notes }; },   // 파일을 바꾸지 않는다
  apply(ctx, answers) { return { moved, edited, created }; },   // answers: decisions에 대한 사용자 답
};
```

| 계획 항목 | 뜻 |
| --- | --- |
| `moves` | 옮길 파일이나 폴더 (`from`, `to`) |
| `edits` | 고칠 파일과 무엇을 고치는지 한 줄 |
| `decisions` | 사람이 골라야 하는 것. 질문, 고를 수 있는 값, 기본값, 이유. AI가 사용자에게 하나씩 묻는다 |
| `notes` | 알려만 줄 것 |

- 기계적인 일(옮기기, 경로 바꾸기, 블록 바꾸기, 설정 바꾸기)은 `apply`가 한다. 토큰이 들지 않는다.
- 판단이 필요한 일은 `decisions`로 내보내고, 스킬이 사용자에게 묻고, 답을 `apply`에 넘긴다. 다음 단계의 `002`에서 "이 문서는 공유인가 개인인가" 같은 것이 여기로 온다.
- 마이그레이션은 이미 된 일을 다시 하지 않는다(같은 결과면 건너뛴다).

### 4.3 첫 마이그레이션: `001` flat → wrapped

예전 배치는 SiloRoot 문서가 프로젝트 맨 위에 바로 있다(`01-log/`~`05-profile/`, `metadata-guide.md`, `writing-guide.md`, 맨 위 `CLAUDE.md`의 관리 블록, `.siloroot/config.json`).

| 할 일 | 방법 |
| --- | --- |
| 알려진 SiloRoot 폴더와 파일 옮기기 | 설정의 `dirs`에 있는 폴더(이름을 바꿨으면 그 이름), `metadata-guide.md`, `writing-guide.md`를 `.siloroot/` 안으로 옮긴다 |
| 문서 안 경로 | 경로는 문서 뿌리 기준이라, 뿌리째 옮기면 바꿀 필요가 없다 |
| 관리 블록 | 맨 위 `CLAUDE.md`에서 SiloRoot 블록을 떼어 `.siloroot/CLAUDE.md`로 옮긴다. 블록을 뗀 뒤 남는 것이 예전 init이 만든 뼈대(프론트매터와 `# 작업 규칙` 제목)뿐이면 `decisions`로 "지울까요?"를 묻는다(기본값 지움). 블록 밖에 사용자가 쓴 내용이 있으면 `decisions`로 "`.siloroot/CLAUDE.md`의 블록 밖으로 옮길까요?"를 묻는다(기본값 그대로 둠). 그 안의 경로는 문서 뿌리 기준이라 옮겨야 맞는 경우가 많다는 이유를 같이 보인다. AI가 정함(만드는 사람 점검 3번) |
| 바깥 git에 올라가 있던 문서 | 예전 init의 `.gitignore`는 `.siloroot/state/`만 뺐으므로 flat 문서가 커밋돼 있을 수 있다. 옮길 파일 중 git이 추적하는 것이 있으면 `decisions`로 묻는다: "계속 git에 올림"(기본값. 제외 줄을 넣지 않고 `git mv`로 옮겨 기록을 잇는다) 또는 "개인 작업 공간으로 뺌"(제외 줄을 넣고, 커밋에서는 지워진 것으로 보인다는 것을 알린다). 이 경우 git으로도 되돌릴 수 있다는 것을 `notes`로 알린다. AI가 정함(점검 1번) |
| 옮기지 않은 것을 가리키는 연결 | 맨 위에 남는 낱 마크다운과 옮기지 않기로 한 폴더를 가리키는 `related`, 백틱 경로는 바꾸지 않는다. `--plan`이 `notes`로 미리 알리고, 적용 뒤 점검에 끊어진 연결로 나온다. 옮긴 뒤 이 파일들은 뷰어에서도 빠진다는 것을 같이 알린다. AI가 정함(점검 5번) |
| 감싼 배치에 필요한 것 | `CLAUDE.local.md` 블록, `.ignore` 줄, git 제외 목록 줄을 init과 같은 방식으로 더한다 |
| 설정 | `layout: "wrapped"`, `schema: 2` |
| 사용자가 직접 만든 SiloRoot 폴더 | 맨 위의 다른 폴더 중 안의 마크다운이 모두 SiloRoot 속성(`type`이 정해진 값)을 가진 폴더는 `decisions`로 "옮길까요?"를 묻는다. 기본값은 옮기지 않음. AI가 정함 |
| 맨 위 `.gitignore` | 예전 init이 만든 것일 수도, 팀 파일일 수도 있다. 내용이 SiloRoot 템플릿과 똑같으면 `decisions`로 "지울까요?"를 묻는다(기본값 그대로 둠). 다르면 손대지 않고 `notes`로 알린다 |

### 4.4 관리 블록과 안내 문서 맞추기

`schema`가 같아도 플러그인 버전이 오르면 관리 블록(예: PR #21의 흐름 나누기 규칙)이나 안내 문서 템플릿이 바뀐다. 업데이트는 마이그레이션 뒤에 init의 "안전한 부분"을 다시 돌린다.

- 관리 블록 바꾸기(`ensureBlock`), 빠진 파일 만들기, `.ignore`와 제외 목록 빠진 줄 더하기
- 이미 있는 안내 문서(`metadata-guide.md` 등)에 새 항목이 빠졌으면 덮어쓰지 않고, 스킬이 템플릿과의 차이를 보여 주며 더할지 묻는다(지금 init의 `warnings` 처리와 같다)
- 끝나면 `plugin`을 지금 버전으로 적는다
- 사용자가 더하지 않겠다고 한 안내 문서 줄은 `.siloroot/state/update-declined.json`에 적고 다음 업데이트에서 다시 묻지 않는다. AI가 정함(점검 4번)

**최신(`upToDate`)의 기준**: 옮길 것(마이그레이션)도, 맞출 것(관리 블록, 빠진 파일, 빠진 줄, 아직 묻지 않은 안내 문서 줄)도 없으면 최신이다. `plugin` 칸만 다를 때는 최신이다. 이때 `--apply`가 파일은 건드리지 않고 `plugin`만 적고, 백업도 만들지 않는다. 스킬은 이 경우 묻지 않고 바로 적는다. AI가 정함(점검 4번)

이를 위해 `scripts/init.mjs`의 블록, 파일, 줄 맞추기를 업데이트가 다시 부를 수 있게 함수로 내보낸다. init의 동작은 바뀌지 않는다.

### 4.5 `scripts/update.mjs`

```
node scripts/update.mjs <프로젝트 폴더> --plan
node scripts/update.mjs <프로젝트 폴더> --apply [--answers <json 파일>]
node scripts/update.mjs <프로젝트 폴더> --restore <백업 이름>
node scripts/update.mjs <프로젝트 폴더> --backups
```

| 명령 | 출력(JSON) |
| --- | --- |
| `--plan` | `from`(지금 schema), `to`(플러그인 SCHEMA), `pluginFrom`, `pluginTo`, `migrations`(각각 id, title, plan), `refresh`(관리 블록, 빠진 파일, 안내 문서 차이), `upToDate`. 파일을 바꾸지 않는다 |
| `--apply` | 백업 이름, 마이그레이션마다 결과, 맞추기 결과, 점검 결과(속성 경고 수, 끊어진 `related`), 실패했으면 어디서 멈췄는지 |
| `--restore` | 되돌린 파일 목록 |
| `--backups` | 백업 목록(이름, 만든 때, from → to) |

- `--apply`에 `decisions`가 있는데 답이 없으면 기본값을 쓰지 않고 멈춘다. 사람이 고를 것을 몰래 고르지 않는다. AI가 정함.
- 마이그레이션은 하나씩 돌리고, 하나가 끝날 때마다 설정의 `schema`를 올린다. 중간에 실패하면 거기서 멈추고, 어디까지 됐는지와 되돌리는 명령을 내보낸다.
- 끝나면 뷰어를 다시 만든다(`viewer/build.mjs`).

### 4.6 백업과 되돌리기

`.siloroot/`는 바깥 저장소의 git에서 빠져 있어 git으로 되돌릴 수 없다. 그래서 바꾸기 전에 파일을 복사해 둔다.

- 자리: `.siloroot/state/backups/<날짜시각>-schema<from>-to<to>/`. 생성물 폴더(`state/`)라 git과 뷰어에서 이미 빠진다. AI가 정함.
- 담는 것: 이번 업데이트가 건드릴 파일 전부의 원래 내용(옮길 폴더 통째, 고칠 파일, `.siloroot/` 밖의 파일 포함)과 `manifest.json`(원래 경로, 새로 만들 경로).
- `state/` 자체는 담지 않는다(뷰어 생성물과 사용 기록이라 다시 만들 수 있다).
- 되돌리기: `manifest.json`대로 원래 내용을 원래 자리에 쓰고, 업데이트가 새로 만든 파일을 지운다.
- 업데이트 뒤에 바뀐 것은 지키기: `manifest.json`에 적용 직후 파일들의 해시를 담는다. 되돌리기 전에 견주어, 업데이트 뒤 고쳐졌거나 새로 생긴 파일이 있으면 멈추고 목록을 보여 준다. 사용자가 "그래도 되돌림"을 고르면 그 파일들을 `state/backups/<이름>/after-update/`에 따로 남긴 뒤 되돌린다. AI가 정함(점검 2번)
- 되돌리기는 최신 백업부터 차례로만 한다. 오래된 백업 하나만 골라 되돌리면 그 뒤 업데이트들과 엉키기 때문이다. AI가 정함(점검 2번)
- 백업은 파일을 실제로 바꿀 때만 만든다(`plugin`만 적는 경우는 만들지 않는다).
- 몇 개까지: 관리 블록 맞추기만 한 백업은 최근 5개를 남긴다. 작업 공간 모양을 바꾼(마이그레이션) 백업은 저절로 지우지 않는다. AI가 정함(점검 4번)

### 4.7 알림

- 세션을 시작할 때(`viewer/notify.mjs --session`) `schema`가 플러그인보다 낮거나 `plugin`이 지금 버전과 다르면 한 덩어리를 더한다.

  ```
  [SiloRoot] 업데이트할 것이 있습니다. /siloroot:update로 미리 보고 올릴 수 있습니다.
  - 작업 공간 모양 1 → 2: 문서를 .siloroot/ 안으로 감싼다
  - 규칙 블록과 안내 문서를 0.4.0에 맞출 수 있습니다
  ```

- 메시지마다 붙는 알림(`UserPromptSubmit`)에는 넣지 않는다. 세션 시작에만 붙어 토큰을 계속 쓰지 않는다.
- 기존 "처리할 일"(피드백 절차)과 섞지 않고 따로 적는다. 처리 절차가 다르기 때문이다.
- 알림을 낼지 판단하는 데 파일을 많이 읽지 않는다. 설정 한 개와 플러그인 버전만 본다.

### 4.7-1 옛 모양에 머물기

**정함 (2026-11-24, 사용자):** 허용한다. 마이그레이션은 거절하고 관리 블록 맞추기만 받을 수 있고, 거절하면 그 알림을 끌 수 있다.

- 거절하면 `config.json`에 `hold`(거절한 목표 모양 번호)를 적는다. 예: 모양 1에서 2로 가는 것을 거절하면 `"hold": 2`.
- 알림: 플러그인 `SCHEMA`가 `hold` 이하면 모양 변경 알림을 내지 않는다. 더 새 모양(예: 3)이 나오면 한 번 다시 알린다. 관리 블록 맞추기 알림은 따로 계속 낸다. AI가 정함
- `/siloroot:update`를 직접 부르면 `hold`와 상관없이 마이그레이션을 보여 주고, 이번에는 올릴지 묻는다. 올리면 `hold`를 지운다.
- 머문 작업 공간도 관리 블록 맞추기를 받으려면 플러그인이 그 모양의 관리 블록을 계속 만들 수 있어야 한다. 그래서 플러그인은 `SUPPORTED_SCHEMAS`(계속 읽고 맞춰 주는 모양 목록)를 가진다. 지금 init이 flat과 wrapped의 블록을 따로 만드는 방식과 같다.
- 어떤 모양을 목록에서 빼는 것(호환을 끊는 것)은 메이저 버전에서만 하고, 그 전 버전부터 세션 시작 알림으로 미리 알린다. AI 제안

### 4.8 `/siloroot:update` 스킬

1. `--plan`을 돌린다. `upToDate`면 "최신입니다"로 끝낸다.
2. 바뀌는 것을 짧게 보여 준다: 마이그레이션 제목, 옮길 것 수와 예, 고칠 파일, 맞출 관리 블록과 안내 문서.
3. 마이그레이션마다 "올릴까요, 지금 모양에 머물까요?"를 묻는다. 머물면 그 마이그레이션은 빼고 `hold`를 적는다(4.7-1).
3-1. 올리기로 한 마이그레이션에 `decisions`가 있으면 하나씩 묻는다(질문, 이유, 고를 값, 기본값).
4. 안내 문서 차이가 있으면 줄마다 더할지 묻는다.
5. 마지막으로 "이대로 올릴까요?"를 묻는다. 승인 없이 적용하지 않는다.
6. 답을 JSON 파일로 쓰고 `--apply`를 돌린다.
7. 결과를 알린다: 백업 이름, 바뀐 것, 점검 결과, 되돌리는 법(`/siloroot:update`에서 "되돌려 줘").
8. 작업 기록(`changelog.md`)에 한 줄을 남긴다.

"되돌려 줘"라고 하면 `--backups`로 목록을 보여 주고 고른 것을 `--restore` 한다.

### 4.9 init과의 관계

- 새 작업 공간: init이 `schema`(지금 SCHEMA)와 `plugin`을 적는다.
- 뒤처진 작업 공간에서 init을 다시 돌리면: 지금처럼 관리 블록만 맞추고, `warnings`에 "작업 공간 모양이 예전 버전입니다. /siloroot:update로 올리세요"를 넣는다. init이 직접 옮기지 않는다.
- init 스킬 설명의 "예전 방식 폴더는 옮기지 않는다"를 "옮기는 것은 `/siloroot:update`가 한다"로 바꾼다.

### 4.10 개발 정책

저장소 `CLAUDE.md`의 "올리기 전 확인"에 더한다.

- 폴더 배치, 문서 위치, 속성 값, 설정 모양이 바뀌면 `SCHEMA`를 올리고 `lib/migrations/`에 마이그레이션과 테스트를 함께 낸다.
- 관리 블록이나 안내 문서 템플릿만 바뀌면 `SCHEMA`는 그대로 둔다. 업데이트의 "맞추기"가 맡는다.
- 옛 모양을 계속 읽는 호환 코드(예: flat 읽기)는 그 모양의 마이그레이션이 나온 뒤에도 당분간 남긴다. 걷어 내는 시점은 열린 질문이다.

## 5. 고른 방법 (Approaches)

| 방법 | 모습 | 고르지 않은 까닭 |
| --- | --- | --- |
| 호환으로 계속 버티기 | 지금처럼 옛 모양을 계속 읽는다 | 구조 분리처럼 큰 변화는 버틸 수 없고, 코드가 모양마다 갈라진다 |
| init이 옮기기까지 하기 | init을 다시 돌리면 알아서 옮긴다 | init은 "없는 것만 만든다"가 약속이라, 같은 명령이 어떤 때는 문서를 옮기면 예측할 수 없다. 미리 보기와 승인, 백업을 넣을 자리도 없다 |
| **따로 업데이트 + 번호 매긴 마이그레이션** (고름) | 작업 공간 버전, 마이그레이션 모음, 알림, `/siloroot:update` | 미리 보기, 승인, 백업, 되돌리기를 한곳에 둘 수 있고, 구조 분리를 마이그레이션 하나로 올릴 수 있다 |

사용자가 정한 것: 업데이트 장치를 먼저 만든다. 저절로 적용하지 않고 알리기만 한다(`shared/ideas/update-migration.md`의 제안 흐름에 사용자가 동의).

## 6. 시험 (만드는 사람에게)

- 옛 모양(flat) 예시 작업 공간 → `--plan`이 옮길 것을 바르게 내놓고 파일은 그대로다.
- `--apply` 뒤 모양이 새로 init한 감싼 작업 공간과 같다(관리 블록, `CLAUDE.local.md`, `.ignore`, 설정). 사용자 문서 내용은 바이트까지 같다.
- 맨 위 `CLAUDE.md`의 블록 밖 내용이 그대로다.
- 한 번 더 `--plan`하면 `upToDate`다.
- `--restore` 뒤 원래 모양과 같다.
- `decisions`에 답이 없으면 `--apply`가 멈춘다.
- 마이그레이션 중간 실패를 흉내 내면 거기서 멈추고 `schema`가 마지막 성공 값이다.
- 세션 시작 알림: 뒤처졌을 때만 나오고, 메시지마다 붙는 알림에는 없다.
- 새 init은 `schema`, `plugin`을 적는다.
- 공백과 한글이 든 폴더(기존 `test/fixtures.mjs`의 방식).

## 7. 만드는 사람에게 맡기는 것
